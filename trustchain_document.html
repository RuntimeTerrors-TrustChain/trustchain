Section 1: The Big Picture — What is TrustChain?

1. The Real-World Problem: Procurement Fraud

Whenever governments or corporations release contracts (tenders) for infrastructure, IT, or supplies, bad actors try to steal those funds. This happens through two separate methods that almost always occur together:

                  ┌────────────────────────────────────────┐
                  │          PROCUREMENT FRAUD             │
                  └──────────────────┬─────────────────────┘
                                     │
         ┌───────────────────────────┴───────────────────────────┐
         ▼                                                       ▼
┌─────────────────────────────────┐             ┌─────────────────────────────────┐
│     1. DOCUMENT-LEVEL FRAUD     │             │     2. NETWORK-LEVEL FRAUD      │
├─────────────────────────────────┤             ├─────────────────────────────────┤
│ • Altered invoice amounts       │             │ • Fake "independent" bidders    │
│ • Pasted signatures/stamps      │             │ • Shared directors / addresses  │
│ • Fabricated financial metrics  │             │ • Circular money laundering     │
└─────────────────────────────────┘             └─────────────────────────────────┘
  1. Document-Level Fraud:
    • A vendor submits an invoice where numbers were altered in Photoshop (e.g., changing ₹1,50,000 to ₹98,50,000) or signatures were copied from other documents.
  2. Network-Level Fraud (Bid Rigging & Shell Companies):
    • The same person creates 4 or 5 "different" companies.
    • When a government tender opens, all 5 companies submit bids to make the competition look legitimate.
    • In reality, they all share the same director, bank account, or address.
    • Once paid, they route the money in circles (A → B → C → A) to fake business activity and evade taxes.

2. Why Existing Solutions Fail

  • Traditional Tools: Check only the document or only the company registration.
    • If a document looks authentic on paper, existing tools approve it—missing the fact that the company belongs to a criminal syndicate.
  • Supervised Machine Learning Models (Random Forest / XGBoost):
    • Require massive sets of labeled fraud data that companies will not share publicly.
    • Function as "black boxes" that cannot explain to an auditor why a vendor was rejected.

3. The TrustChain Solution: Multi-Signal Fusion

TrustChain combines both verification layers into one system using mathematical, rule-based forensics and graph theory (no black-box machine learning required):

  • Layer B (Entity Relationship Graph): Uses graph algorithms (Louvain Community Detection and Cycle Detection) to find hidden shell networks and circular money flows.

Section 2: Environment Setup & Directory Architecture

1. The Virtual Environment (venv) Concept

Why do we use a virtual environment?
When you install Python libraries on your computer globally, different projects can have conflicting versions. A venv is an isolated container inside your project folder. Any package installed inside (venv) stays inside this project without affecting the rest of your computer.

Commands to set up the environment:

# 1. Create a new folder and enter it
mkdir trustchain
cd trustchain

# 2. Create the virtual environment named 'venv'
python -m venv venv

# 3. Activate the virtual environment
# Windows (PowerShell):
.\venv\Scripts\Activate.ps1
# Windows (Command Prompt):
.\venv\Scripts\activate.bat
# macOS / Linux:
source venv/bin/activate

(When activated, your terminal prompt will show (venv) at the beginning).

Section 3: Project Configuration (config.py)

1. Why config.py Exists (The Single Source of Truth)

In poorly architected projects, developers hardcode "magic numbers" everywhere (e.g., typing 50000 in transaction files, 90 in image files, and 70 in scoring files).

If a judge asks "What happens if we lower the risk threshold to 60?", a messy project requires editing multiple files and risks introducing inconsistent behavior or bugs.

In TrustChain, config.py is the central control room. Every major module imports its thresholds, weights, deterministic seed, and file paths from this one file.

This provides:

  • Centralized configuration — thresholds are defined once.
  • Consistency — every module uses the same values.
  • Maintainability — changing a threshold requires editing one location.
  • Explainability — important numerical decisions can be traced to named constants.
  • Deterministic demonstrations — the same seed produces repeatable synthetic data and graph behavior.
  • Easy experimentation — thresholds can be modified without searching through the entire codebase.

4. Module A: Document Forensics Thresholds

ELA_JPEG_QUALITY = 90
ELA_AMPLIFICATION_SCALE = 20
ELA_HOTSPOT_PERCENTILE = 85
BENFORD_MIN_SAMPLE_SIZE = 30

These constants control the document-forensics pipeline.

🔹 ELA_JPEG_QUALITY = 90

What it controls:
The JPEG quality used when an image is re-encoded during Error Level Analysis (ELA).

Forensic Logic

ELA compares an original image with a recompressed version.

JPEG compression works through operations including:

  • dividing the image into blocks,
  • applying a Discrete Cosine Transform (DCT),
  • quantizing frequency information,
  • reconstructing the image.

When a document contains regions that have undergone different compression histories, those regions may respond differently during recompression.

A quality level of 90 provides a practical high-quality recompression baseline for the prototype.

Why not 100?

At extremely high quality, the recompressed image may introduce very little additional compression error, reducing the visible ELA signal.

Why not 50?

Aggressive compression can introduce artifacts throughout the entire document, increasing background noise and making genuine anomalies harder to isolate.

Important Interpretation

ELA is a forensic signal, not proof of manipulation by itself.

An ELA hotspot should be correlated with other evidence such as:

  • metadata,
  • document structure,
  • visual inspection,
  • OCR/text consistency,
  • transaction behavior,
  • graph relationships.

🔹 ELA_AMPLIFICATION_SCALE = 20

What it controls:
The multiplier applied to raw pixel-level differences.

Suppose the original/recompressed difference for a pixel is:

Raw difference = 5

On a 0–255 brightness scale, that difference is visually subtle.

After amplification:

5 × 20 = 100

The difference becomes much easier to visualize.

Engineering Trade-Off

Too little amplification:

Weak signal
   ↓
Tampering may remain difficult to see

Too much amplification:

Scanner grain + paper texture + JPEG noise
   ↓
Large number of false hotspots

Therefore, 20 is a practical visualization parameter for the prototype and can be calibrated against the project's document dataset.

🔹 ELA_HOTSPOT_PERCENTILE = 85

What it controls:
The percentile used to identify high-intensity regions in the ELA difference map.

Conceptually:

0% ─────────────────────────────────── 100%
       Background variation       Strongest signals
                                  ↑
                                85th %

The top portion of the error distribution is retained as candidate hotspot information.

Why 85?

A percentile-based threshold adapts to the image instead of relying on one absolute pixel value.

  • A lower threshold can generate too many candidate regions.
  • An extremely high threshold can miss weaker anomalies.
  • 85 provides a practical starting point for retaining strong signals while suppressing much of the background variation.

This remains a configurable heuristic rather than a universal forensic threshold.

🔹 BENFORD_MIN_SAMPLE_SIZE = 30

What it controls:
The minimum number of numerical observations required before applying Benford's Law analysis.

Benford's Law models the expected probability of a leading digit:

P(d) = \log_{10}\left(1+\frac{1}{d}\right)

where:

d ∈ {1,2,3,4,5,6,7,8,9}

Statistical Logic

With very few observations, the observed leading-digit distribution can vary substantially simply because of sampling variability.

For example, 3 invoices cannot provide a stable empirical distribution across 9 possible leading digits.

Therefore, TrustChain requires a minimum sample before using the distribution as a signal.

The value 30 is a practical prototype threshold intended to reduce over-interpretation of very small datasets. It should not be treated as a universal guarantee of statistical significance.

🔹 FUZZY_MATCH_THRESHOLD = 90.0

What it controls:
The minimum string similarity required before two textual attributes are considered sufficiently similar for a potential graph relationship.

Example:

Company A:
Plot 42, Okhla Industrial Area, Phase-1, New Delhi

Company B:
42 Okhla Ind Area Phase 1 New Delhi

An exact string comparison would fail: company_a == company_b.

A fuzzy-matching algorithm can tolerate punctuation differences, word-order differences, abbreviations, and minor typographical changes.

Why 90.0?

A high threshold makes the entity-resolution process relatively conservative. The value 90.0 is therefore a TrustChain prototype design choice intended to balance false links versus missed relationships.

🔹 SHELL_CLUSTER_MAX_SIZE = 8

What it controls:
The maximum number of entities considered within the prototype's suspicious small-cluster heuristic.

A tightly interconnected group containing only a few entities can be structurally interesting because it may represent shared directors, addresses, suppliers, or financial relationships. The value 8 is therefore a prototype heuristic rather than a universal definition of a shell-company ring.

🔹 SHELL_CLUSTER_MIN_DENSITY = 0.5

What it controls:
The minimum graph density used by the suspicious-cluster heuristic.

For an undirected graph:

D = \frac{2E}{V(V-1)}

where E = number of edges, and V = number of vertices.

TrustChain uses Density ≥ 0.5 as one structural signal for a potentially suspicious tightly connected cluster.

Important Interpretation

High graph density alone does not establish fraud. Companies can legitimately share directors, registered offices, suppliers, parent organizations, and financial relationships. Therefore, graph density is treated as one component of the larger evidence-fusion system.

🔹 MAX_CYCLE_HOP_LIMIT = 6

What it controls:
The maximum search depth used when looking for directed circular transaction flows (e.g. A → B → C → A). The prototype permits cycles up to six hops to safeguard computation and limit deep cycle searches in dense graphs.

def inject_circular_chain(
    cluster_members: List[str],
    cycle_amount: float = 250000.0
) -> Tuple[List[Dict], Dict]:
    """Injects a 3-hop circular invoicing ring (A -> B -> C -> A)."""
    transactions = []

    hop_count = min(len(cluster_members), 3)
    cycle_nodes = cluster_members[:hop_count]

    base_date = datetime.now() - timedelta(days=15)

    for i in range(hop_count):
        sender = cycle_nodes[i]
        receiver = cycle_nodes[(i + 1) % hop_count]

        txn_amount = cycle_amount * (1.0 - (i * 0.01))

        txn_date = (
            base_date
            + timedelta(
                days=i * 2,
                hours=random.randint(1, 5)
            )
        )

        transactions.append({
            "transaction_id": (
                f"TXN-CYCLE-{sender[-4:]}-{receiver[-4:]}"
            ),
            "from_entity": sender,
            "to_entity": receiver,
            "amount": round(float(txn_amount), 2),
            "date": txn_date.strftime("%Y-%m-%d %H:%M:%S"),

import networkx as nx
from collections import defaultdict
from rapidfuzz import fuzz
from typing import List, Dict
from config import FUZZY_MATCH_THRESHOLD

def build_entity_graph(entities: List[Dict]) -> nx.Graph:
    """
    Builds an undirected graph where edges represent shared attributes 
    (directors, addresses, phones, bank accounts) between entities.
    """
    G = nx.Graph()

    # 1. Add all entities as nodes
    for entity in entities:
        G.add_node(
            entity["entity_id"],
            name=entity.get("name", ""),
            directors=entity.get("director_names", []),
            address=entity.get("registered_address", ""),
            phone=entity.get("phone", ""),
            bank_account=entity.get("bank_account", "")
        )

    # 2. Exact attribute indexing
    phone_map = defaultdict(list)
    bank_map = defaultdict(list)
    
    for e in entities:
        eid = e["entity_id"]
        if e.get("phone"):
            phone_map[e["phone"]].append(eid)
        if e.get("bank_account"):
            bank_map[e["bank_account"]].append(eid)

    # Add edges for exact matches
    for field_name, attr_map in [("phone", phone_map), ("bank_account", bank_map)]:
        for val, ids in attr_map.items():
            if len(ids) > 1:
                for i in range(len(ids)):
                    for j in range(i + 1, len(ids)):
                        G.add_edge(ids[i], ids[j], shared_field=field_name, shared_value=val)

    # 3. Fuzzy matching for Directors and Addresses
    n = len(entities)
    for i in range(n):
        e1 = entities[i]
        id1 = e1["entity_id"]
        
        for j in range(i + 1, n):
            e2 = entities[j]
            id2 = e2["entity_id"]

            # Address fuzzy comparison
            addr1, addr2 = e1.get("registered_address", ""), e2.get("registered_address", "")
            if addr1 and addr2:
                if fuzz.token_sort_ratio(addr1, addr2) >= FUZZY_MATCH_THRESHOLD:
                    G.add_edge(id1, id2, shared_field="registered_address", shared_value=addr1)

            # Director fuzzy comparison
            for d1 in e1.get("director_names", []):

import networkx as nx
import networkx.algorithms.community as nx_comm
from typing import List, Dict
from config import GLOBAL_SEED, SHELL_CLUSTER_MAX_SIZE, SHELL_CLUSTER_MIN_DENSITY

def detect_shell_clusters(G: nx.Graph) -> List[Dict]:
    """
    Partitions the graph using Louvain community detection and flags
    small, high-density clusters characteristic of shell rings.
    """
    if len(G.nodes) == 0 or len(G.edges) == 0:
        return []

    communities = nx_comm.louvain_communities(G, seed=GLOBAL_SEED)
    suspicious_clusters = []

    for idx, community in enumerate(communities):
        if len(community) < 2:
            continue

        subgraph = G.subgraph(community)
        density = nx.density(subgraph)

        if len(community) <= SHELL_CLUSTER_MAX_SIZE and density >= SHELL_CLUSTER_MIN_DENSITY:
            shared_links = []
            for u, v, d in subgraph.edges(data=True):
                shared_links.append([u, v, f"{d.get('shared_field')}:{d.get('shared_value')}"])

            suspicious_clusters.append({
                "cluster_id": f"CLUSTER-{idx+1:02d}",
                "members": list(community),
                "density": round(density, 2),
                "size": len(community),
                "shared_links": shared_links
            })

    return suspicious_clusters

Part 3: Directed Circular Invoicing Detection (modules/graph/cycles.py)

import networkx as nx
from typing import List, Dict

def detect_circular_invoicing(transactions: List[Dict], max_hops: int = 4) -> List[Dict]:
    """
    Builds a directed financial graph and finds high-confidence tight cycles (3-4 hops).
    Filters out long, noisy incidental loops.
    """
    DG = nx.DiGraph()

    for txn in transactions:
        u = txn["from_entity"]
        v = txn["to_entity"]
        if DG.has_edge(u, v):
            DG[u][v]["amount"] += txn["amount"]
        else:
            DG.add_edge(u, v, amount=txn["amount"])

    raw_cycles = list(nx.simple_cycles(DG, length_bound=max_hops))
    flagged_cycles = []

    for cycle in raw_cycles:
        if len(cycle) < 3:
            continue  # Ignore 2-way refunds

        total_flow = sum(
            DG[cycle[i]][cycle[(i + 1) % len(cycle)]]["amount"]
            for i in range(len(cycle))
        )

        flagged_cycles.append({
            "path": cycle,
            "hop_count": len(cycle),
            "total_flow": round(total_flow, 2)
        })

    flagged_cycles.sort(key=lambda c: (c["hop_count"], -c["total_flow"]))
    return flagged_cycles

def detect_structuring(transactions: List[Dict]) -> List[Dict]:
    """
    Identifies entities issuing repeated transactions just under the reporting threshold.
    """
    if not transactions:
        return []

    df = pd.DataFrame(transactions)
    df["date"] = pd.to_datetime(df["date"])

    lower_bound = STRUCTURING_THRESHOLD * STRUCTURING_NEAR_BAND
    upper_bound = STRUCTURING_THRESHOLD

    near_threshold = df[(df["amount"] >= lower_bound) & (df["amount"] < upper_bound)]
    if near_threshold.empty:
        return []

    structuring_flags = (
        near_threshold.groupby(["from_entity", pd.Grouper(key="date", freq="7D")])
        .agg(txn_count=("amount", "count"), total_amount=("amount", "sum"))
        .reset_index()
    )

    flagged = structuring_flags[structuring_flags["txn_count"] >= STRUCTURING_MIN_TXNS]
    
    results = []
    for _, row in flagged.iterrows():
        results.append({
            "entity_id": row["from_entity"],
            "txn_count": int(row["txn_count"]),
            "total_amount": float(row["total_amount"]),
            "window_start": str(row["date"])
        })
    return results

def compute_combined_risk_score(doc_result: Dict[str, Any], graph_result: Dict[str, Any]) -> Dict[str, Any]:
    """
    Fuses Document Forensics (Layer A) and Graph Intelligence (Layer B)
    using transparent rule-escalation logic.
    """
    doc_score = float(doc_result.get("authenticity_score", 0.0))
    graph_score = float(graph_result.get("graph_risk_score", 0.0))

    # 1. Base Weighted Score
    base_score = (WEIGHT_DOCUMENT * doc_score) + (WEIGHT_GRAPH * graph_score)
    escalation = 0.0
    escalation_reasons: List[str] = []

    # Escalation Rule 1: Tampered Document + Belongs to Shell Cluster
    has_tamper = doc_score >= 40.0 or len(doc_result.get("ela_hotspots", [])) > 0
    in_shell_cluster = (graph_result.get("cluster_size", 1) > 1) or (graph_result.get("cluster_density", 0.0) >= 0.5)

    if has_tamper and in_shell_cluster:
        escalation += ESCALATION_CLUSTER_AND_TAMPER
        escalation_reasons.append(
            "🚨 CRITICAL ESCALATION: Tampered document detected AND entity belongs to a linked shell cluster "
            "— combined fraud signal indicates organized bidding fraud."
        )

    # Escalation Rule 2: Inconsistency + Circular Fund Routing
    has_meta_or_ela = len(doc_result.get("metadata_flags", [])) > 0 or len(doc_result.get("ela_hotspots", [])) > 0
    has_cycles = len(graph_result.get("cycles_involved", [])) > 0

    if has_meta_or_ela and has_cycles:
        escalation += ESCALATION_CYCLE_AND_METADATA
        escalation_reasons.append(
            "⚠️ CROSS-LAYER FLAG: Document forensic anomalies coincide with active circular fund routing involving this entity."
        )

    # Final Fused Score
    final_score = min(100.0, base_score + escalation)

    # Risk Band Determination
    if final_score >= SCORE_BAND_HIGH:
        risk_band = "HIGH"
    elif final_score >= SCORE_BAND_MEDIUM:
        risk_band = "MEDIUM"
    else:
        risk_band = "LOW"

    # Combine all explainable reasons cleanly
    all_reasons = (
        doc_result.get("reasons", [])
        + graph_result.get("reasons", [])
        + escalation_reasons
    )

    return {
        "entity_id": doc_result.get("entity_id") or graph_result.get("entity_id", "UNKNOWN"),
        "final_risk_score": round(final_score, 1),
        "risk_band": risk_band,
        "base_score": round(base_score, 1),
        "escalation_applied": round(escalation, 1),
        "reasons": all_reasons
    }

3. Mathematical Metrics Calculation

  1. Accuracy:
    \text{Accuracy} = \frac{\text{TP} + \text{TN}}{\text{Total Entities}} = \frac{12 + 120}{132} = \mathbf{100.0\%}
  2. Recall (Sensitivity):
    \text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}} = \frac{12}{12 + 0} = \mathbf{100.0\%}
  3. Precision (Positive Predictive Value):
    \text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}} = \frac{12}{12 + 0} = \mathbf{100.0\%}
  4. F1-Score:
    \text{F1} = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}} = \mathbf{100.0\%}
